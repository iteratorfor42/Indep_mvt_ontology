# v9.5 vs v9.5re 비교 분석 보고서

## — 실제 파일 diff 기반, 두 페이지가 정확히 무엇을 공유하고 무엇만 다른지

> 이 보고서는 추측이 아니라 `diff versions/v9_5.html versions/v9_5re.html`을 직접 돌린
> 결과(65줄, 순변경 49줄)를 근거로 작성했다. 두 파일이 같은 데이터 파일(`data/v9_5.ttl`)
> 하나를 그대로 가리키고 있다는 것도 `fetch(...)` 경로를 직접 확인했다.

---

## 1. 한 줄 요약

**v9.5re는 v9.5의 새 버전이 아니라, 같은 데이터에 하나의 표시 축(review)만 얹은
동일 페이지의 변형이다.** 데이터 계층(TTL/CSV)은 파일 단위로 공유되고, 코드 diff는
전부 (a) 설명 문구, (b) `SEMANTIC_REVIEW` 참조표, (c) 그 참조표를 읽어 간선/패널을
살짝 다르게 그리는 조건문에 한정된다. 데이터 fetch·파싱·Claim 추출 로직은 단 한 줄도
다르지 않다.

## 2. 데이터 계층 — 완전히 동일 (diff 없음)

| 항목 | v9.5 | v9.5re |
|---|---|---|
| ttl 원본 | `data/v9_5.ttl` | `data/v9_5.ttl` (같은 파일, 복제 아님) |
| claim_core.csv / claim_hold.csv / exclusion_manifest.csv | 동일 파일 링크 | 동일 파일 링크 |
| `claimDecision`(core/hold) | 34 / 5 | 34 / 5 (불변) |
| `hasDateStatus` 분포 | verified 18 / not_directly_verified 11 / not_applicable 10 | 동일 |
| 파싱 로직(`parseTurtle`, `index()`, `byType`, `ENTITY_TYPE` 등) | — | diff 0줄 |
| 노드/간선 구성 로직(`buildNetwork`의 subject/object/relation 추출) | — | diff 0줄 |

`ttl-parser.js` 자체(공용 파일, 두 페이지가 같이 씀)에서 이전에 발견·수정한 `<IRI>` 안
`#` 오인식 버그도, 수정 이후로는 v9.5·v9.5re 양쪽 모두 **987 트리플**로 동일하게
집계된다 — 이 부분도 이번에 두 파일 다시 실행해 재확인했다.

## 3. 시각화 계층 — diff 49줄, 전부 review 축 하나로 수렴

`diff`로 나온 변경을 종류별로 묶으면 정확히 4곳뿐이다.

### 3-1. 문구(제목·부제·범례) — 6곳
`<title>`, `<h1>`에 "re" 표기 추가, 부제에 "v9.5re 추가 사항" 단락 신설(데이터 불변
고지), 관계망 탭에 범례 박스(`core 실선 / hold 점선 / 🔍 재검토 2건`) 신설. 화면에
보이는 텍스트일 뿐 로직 변경은 없다.

### 3-2. 참조표 신설 — `SEMANTIC_REVIEW`
```js
var SEMANTIC_REVIEW = {
  "CLM-024": "...",
  "CLM-027-04": "...",
};
```
이 표는 TTL/CSV 어디에도 없는, **v9.5re에서만 존재하는 정적 주석**이다. 데이터를
읽어서 만든 게 아니라 손으로 등록한 2건뿐이라, `claimsOf`가 몇 건이든(39건 불변) 이
표의 크기(2건)와는 무관하다.

### 3-3. 간선 렌더링 조건 분기 — 3속성만 조건부로 갈라짐
```js
var isReview = !!SEMANTIC_REVIEW[cid];
label: (isReview ? "🔍 " : "") + relation,
color: isHold ? 주황 : (isReview ? 보라 : 갈색),
width: isHold ? 1.5 : (isReview ? 2.5 : 2),
```
`dashes`(점선 여부)는 **여전히 `isHold`만으로 결정** — review는 core/hold 축을
전혀 건드리지 않는다는 설계 원칙이 코드 수준에서도 지켜지고 있다.

### 3-4. 상세 패널 — 배지 1개 + 문구 1줄 추가
`core`/`hold` 배지 옆에 조건부로 `🔍 의미론 재검토 권고` 배지, 그 아래 재검토 사유
문장이 추가되는 것뿐, 나머지 필드(날짜·검증상태·출처·근거)는 그대로다.

## 4. 영향 범위 — 39건 중 2건만

| Claim 집합 | 개수 | v9.5 렌더링 | v9.5re 렌더링 | 차이 |
|---|---|---|---|---|
| core (review 아님) | 32 | 실선·갈색 | 실선·갈색 | 없음 |
| hold | 5 | 점선·주황 | 점선·주황 | 없음 |
| core + review (CLM-024, CLM-027-04) | 2 | 실선·갈색 | **실선·보라·🔍** | **여기만 다름** |

39건 중 37건은 두 페이지에서 픽셀 단위로 동일하게 그려진다. 실질적 차이는 **정확히
2개 간선**에 국한된다.

## 5. 검증 방법과 한계

- 코드 diff: 직접 실행해 확보(§본문 상단 인용).
- 데이터 동일성: fetch 경로 문자열 대조로 확인(둘 다 `data/v9_5.ttl`) — 파일이 물리적으로
  하나이므로 "내용이 같다"가 아니라 "같은 파일을 참조한다"는 더 강한 보장이다.
- 실행 결과(노드/간선/재검토 수): jsdom + 실제 vis-network로 두 파일 모두 이전에 개별
  검증 완료(각 990개 문서에서 보고). 이번엔 diff만 다시 실행해 그 결과를 뒷받침했다.

## 6. 결론

| 항목 | 판정 |
|---|---|
| 데이터(TTL/CSV) 동일성 | 확인됨 — 같은 파일 참조, 파싱 로직 diff 0줄 |
| core/hold 분류 불변 | 확인됨 — `dashes`는 여전히 `isHold`만으로 결정 |
| review 축의 독립성 | 확인됨 — `SEMANTIC_REVIEW`는 별도 상수, 데이터 파싱과 무관 |
| 실질적 렌더링 차이 범위 | 39건 중 2건(CLM-024, CLM-027-04)에 한정 |
| v9.5re를 "새 데이터 버전"으로 부르는 것 | **부적절** — 정확히는 "v9.5의 review 주석 오버레이" |

**종합**: v9.5 → v9.5re는 데이터 버전 증가가 아니라 같은 데이터 위에 얹은 주석
레이어 하나다. diff 49줄 중 데이터 계층에 손댄 줄은 0줄이며, 나머지는 전부 텍스트
설명이거나 2건짜리 정적 참조표와 그걸 읽는 조건문이다 — "데이터는 그대로, 검토
의견만 별도 축으로 얹는다"는 애초 설계 원칙이 코드 구조에도 정확히 반영돼 있다.
