## I. 전체 개관 (간결본)

일제강점기 독립운동-근대학교 온톨로지는 두 갈래로 발전했다.

- **본체 (v1~v8)**: Prof. 김현 & Prof. 김바로 style 계승
  이항관계(v1) → 사건유형별 클래스(v2) → 단일 Event 스키마 정착(v3)
   → 편찬 메타데이터·도메인 확장(v4~v5) → 사실 검증(v6~v7) 
   → 불확실성 자체의 모델링(`hasValidationStatus`, 신흥강습소 실체분리, v8).
- **Provenance 트랙 (ver2~ver5, v9.1~v9.5)**: v8 인스턴스가 실제로
  근거를 갖췄는지 재검증하기 위해 별도로 시작한 Claim 중심 병렬 데이터셋.
  49개 원본 항목 → 55개 Claim으로 분해 → 34 Core + 5 Hold(TTL 반영,
  987 트리플) + 16 Exclusion(CSV만 보관).
- **시각화 (v6~v10, dh-webpage 저장소)**: 본체·Provenance 트랙 데이터를
  브라우저에서 읽어 그리는 뷰어들. `v9_5re.html`에서 데이터는 그대로 두고
  의미론 재검토 표시축(`SEMANTIC_REVIEW`)만 추가했고, `v10.html`은
  여기에 국가보훈부 공훈전자사료관 API 연동을 시도했으나 **HTTP-only
  API·가용성 불안정·서버 XML 명세 위반 등으로 아직 실사용 가능한
  상태가 아님** — 현재도 진행 중인 미해결 과제.

세 갈래 모두 "김바로, 『제도-인사 온톨로지 설계』"의 사건모델(`:Event`
단일 스키마)을 공통 뿌리로 삼지만, Provenance 트랙은 그 모델이 표현하지
못하던 "관계 자체의 확실성"을 담기 위해 완전히 다른 스키마(Claim/
Evidence/Source 분리)로 갈라져 나온 것이며, v8의 "다음 버전"이 아니라
병렬 재검증 트랙이다.

## II. 상세 이력

### 0. 전체 개요 — 세 가지 접근(시기/방법/국면)

- **스키마 전환기 (v1~v3)**: 데이터를 어떤 구조로 담을지 결정. 이항관계
  → 사건유형별 클래스 → 원 논문의 단일 Event 스키마.
- **정합성·범위 확장기 (v4~v5)**: 편찬 정보(누가·언제) 정리, 중복·충돌
  개체 해소, 도메인을 "구한말 관공립학교"에서 "독립운동-근대학교
  네트워크"로 확장.
- **사실 검증·불확실성 모델링기 (v6~v8)**: 실제 역사적 사실을 재검색해
  확정하거나, 확정 못 하는 상태 자체를 구조화.

### 1. v1   이항관계

- *솔직하게 밝힙니다.* 
- 60일 이내에 작업을 끝낼 수 있게끔 **클로드와 챗지피티를 이용해 이항관계가 나오는 인물과 사건을 먼저 조사**했습니다.
- 나머지 작업 경우 논리 전개는 제가 했고, 시각화 등 부가적인 건 클로드와 챗지피티 활용했습니다.
- (특히 재검증 과정에서 csv와 보고서 수치 분석[=정합성 분석]은 클로드 이용했습니다.)

### 2. v1 → v2 — 이항관계에서 사건유형별 클래스로

v1은 `["이승훈", "오산학교", "설립"]` 배열을 그대로 `forceLink`에 꽂는
D3.js 그래프였다. v2에서 OWL/Turtle로 전환하며 `FoundingEvent`·
`RoleEvent`·`AppointmentEvent`처럼 사건유형별 클래스를 만들었다.

### 3. v2 → v3 — Event 모델을 기본 틀로 채택

김바로 박사논문의 Event 중심 설계를 기본 모델로 채택해 단일 `:Event`
클래스로 통합. 47개체·627 트리플, Protégé 정상 파싱 확인. `locatedIn`
류 6개 관계는 Event로 바꾸지 않고 조직의 정적 상태로 남기는 것은
원 논문이 아니라 프로젝트가 임의로 정한 해석이다.

### 4. v3 → v4 — 편찬 메타데이터와 정합성 정리

`hasCompiler`/`hascompiledTime` 미기입 65건 보강, `:백오인사건` Group/
Event 이중 타입 해소, 중복 개체(`:이승훈설립오산학교_01`) 제거.

### 5. v4 → v5 — 편찬자 실체화, 도메인 확장

`hasCompiler` placeholder를 `:iteratorfor42`로 치환(68회). 다만
v5 자신은 이 단계에서 다음 문제를 방치했다: 오산학교-대성학교
`succeedByPersonTo`가 근거(hasBibo) 없이 서사만으로 단정돼 있었고,
안명근체포 Event가 `hasEventType :임명`으로 잘못 분류된 채 방치됐으며
(`:체포` Term 자체가 아직 없었음), 역사적 사건 6개 전부가
`hasEestimation` 없이 "1월 1일" sentinel로 남아 있었다.

### 6. v5 → v6 — 3회차 검토안 반영

**필수 수정 4건**: 안명근체포 유형(`:체포`)·시간(1910-12-01) 정정,
오산-대성 승계관계 삭제, 오산학교 개교일 1907-12-24 확정(다출처
일치 근거, 단 이 확신은 훗날 v9 ver2에서 재반박됨 — §III 참조),
안명근체포→안악사건→백오인사건 2단계 확대구조 신설.
**추가 검증 날짜 5건**: 삼일운동(1919-03-01)·봉오동전투·청산리전투·
조선물산장려회(1920-08-23) 확정, 연도만 아는 설립 Event 일괄 추정
플래그 부여. 이 시점까지도 소속/참여 Event 12+9건은 언급조차 없이
공란이었다(v6 changelog에 미기재).

### 7. v6 → v7 — 날짜 자동상속 금지 원칙의 최초 대규모 적용

신민회/임시정부 소속 12건에 Year 추정 부여, 3·1운동 참여 9건 중
6건 확정·3건(정춘수·박희도·조만식) 예외 처리. 설립→공동설립(`:공동설립`
Term 신설) 구분. 이종일의 "경영"이 보성학교 전체가 아니라 부속 인쇄소
보성사였음을 코멘트로 처음 인지했으나(v7), 트리플 자체는 아직
`:보성학교`로 남아 있어 "코멘트가 데이터를 정정하는" 결함이 존재했다.

### 8. v7 → v8 — 불확실성 자체의 모델링

임시정부 소속 4건 개별 재검증(이승만 1919-09-11 확정, 이동휘
1919-09±2개월), 이종일-보성사 구조 분리(`:보성사` Group 신설, v7의
결함 해소), `hasValidationStatus` 신설(김좌진-신민회를 "검증보류"로
격리 — 원 논문에 없던 속성을 즉석에서 추가한 것), 신흥강습소/
신흥무관학교 실체 분리(개칭 이벤트 존재 자체의 불확실성 모델링).

## III. Provenance 트랙 상세 (ver2 ~ v9.5)

v8을 검증하는 별도 트랙. **v8의 다음 버전이 아니다.**

- **ver2~ver5(방법론 설계)**: URL 팩트체크(ver2) → Claim/Evidence/
  Source 분리(ver3) → 김좌진 정정·Claim 분해(ver4) → 설계 승인,
  Rule G-01~G-08 확정(ver5). ver2 단계에서 「이승훈」 항목 원문을 직접
  열어보니 "11월 24일"로 되어 있어, v6이 "복수 출처 일치"로 확정했던
  "12월 24일"의 근거 자체가 두 계열 출처를 짜깁기한 것이었음이 드러남.
- **v9 초안~완성본**: 49개 항목 → 43개 행(오판 6개 UNMAPPED) → 원본
  마스터리스트 대조로 진짜 누락 3건(신흥무관학교·대한독립군·양기탁)
  복원 → 46개 매핑 항목 확보 → 그중 다수 항목이 §4의 6개 표준 패턴에
  따라 복수 Claim으로 분해되며(예: 대성학교 1항목→CLM-002/011 2건,
  오산학교 1항목→CLM-OSAN-01/02 2건) 최종 55개 Claim 완성(커버리지
  확보, 아직 신뢰도 필터링 전).
- **v9.1**: 구조 검증. CLM-023(SRC 오배정)·CLM-010(비표준 precision)
  수정, TTL 1155 트리플.
- **v9.2**: 39개 포함(당시 "High-confidence"로 잘못 명명) + 16 exclusion
  최초 분리. 재검증 중 CLM-006 컬럼 밀림·CLM-023 재발·CLM-010 재발·
  안악사건(item 15) 완전 누락 발견·수정. TTL 928 트리플.
- **v9.3**: 39개를 34 Core + 5 Hold로 재분류, 4단계 판정(유지/수정/
  보류/제외) 확정. TTL 969 트리플.
- **v9.4**: Claim 문장·URI·relation 의미 정합성 6건 수정(CLM-014
  subject 오류, CLM-003 방향 불일치 등). `not_applicable` vocab 신설.
  TTL 972 트리플.
- **v9.5**: date_status 완전 정합화(빈 값 0건). 1차 제안 규칙("date_value
  없음→전부 not_applicable")이 자기모순임을 재검토에서 발견해 폐기,
  "Claim의 시간적 의미" 기준으로 재수립(not_applicable 9건/
  not_directly_verified 6건). TTL **987 트리플**, Core 34 + Hold 5 +
  Exclusion 16 = 55.
- **[갱신] CLM-023 재발 횟수에 대한 정정**: 위 v9.1~v9.2 항목은 CLM-023이
  두 차례(v9.1 최초 수정, v9.2 SRC 재배정 재발 수정) 수정됐다고 기록한다.
  이전 요약본 중에는 v9.3에서도 CLM-023이 "또 재누락"되어 이를
  "개별 버그가 아니라 파이프라인 재현성 문제"로 격상했다는 서술이
  있었으나, CLM-023 자신의 change_history(v9.3 항목: "유지 — 근거·표현
  모두 이상 없음, claim_core.csv 유지")에는 이 세 번째 재발이 기록되어
  있지 않다. 따라서 v9.3 재발 여부는 v9.3 원본 파일을 직접 대조하기
  전까지 확정하지 않는다. change_history로 확인되는 것은 최소 2회
  (v9.1→v9.2) 재발이며, "개별 버그가 아니라 파이프라인 재현성 문제"라는
  평가 자체는 이 2회만으로도 유지될 수 있다.
- **사후 발견(3자 비교분석에서, [갱신] 과잉확신 정정)**: 3자비교분석은
  core+hold 39건 안에 `CLM-014`(`:안악사건 --related_to--> :105인사건`)
  가 존재함을 확인했다. 다만 `relation=related_to`가 인과관계·단순연관·
  사건 확대를 전혀 구분하지 못하는 범용 값이라, 이 Claim만으로 "안악사건
  →105인사건"이 어떤 종류의 관계인지는 특정되지 않는다. 또한 "안명근체포
  →안악사건" 전반부에 해당하는, 안명근 개인을 subject·object로 갖는
  Claim은 현재 core+hold 39건 어디에도 없다. `CLM-014`의 change_history에는
  "v9.4: subject_uri를 :안명근(인물)에서 :안악사건(사건)으로 정정"이라는
  기록이 있어 이 변경이 v9.4 시점에 일어났다는 것 자체는 change_history
  원문으로 확인되지만, **이 change_history의 자기 서술만으로 "안명근
  엔티티가 유실됐다"고 단정할 수는 없다** — 3자비교분석 §6-3도 "곧바로
  유실됐다고 단정해서는 안 되며, 확정하려면 버전별 파일 대조가 필요하다"고
  명시적으로 유보하고 있다. 따라서 정확한 현재 상태는: v8이 예감한
  "의미 중복"은 (1) relation 어휘 미비, (2) 인물 엔티티 부재라는 두
  갈래로 세분화됐으나, (2)의 원인이 v9.4에서의 의도적 정정인지 의도치
  않은 유실인지는 change_history상 전자로 기록되어 있을 뿐 독립적인
  버전 대조로 확정된 것은 아니다.

## IV. 시각화 트랙 상세 (v6 ~ v10, dh-webpage)

- `v6.html`/`v8_d3style.html`/`v8_with_gonghun.html`: TTL을 fetch로
  읽어 GIS+관계망 2탭으로 렌더링. v1의 D3 코드 자산을 v8 데이터로
  재현하는 과정에서 버그 3건(숨은 탭 초기화, CSS grid 높이,
  `versions-data.js` 스키마 사고) 발견·수정.
- `v9_5.html`: Provenance 트랙 최초 뷰어. `claimDecision`(core 실선/
  hold 점선)으로 신뢰도 구분.
- `v9_5re.html`: 데이터는 `v9_5.html`과 완전히 동일, `SEMANTIC_REVIEW`
  참조표(CLM-024·CLM-027-04 2건)로 "의미론 재검토 권고" 표시축만
  추가. diff 기준으로도 데이터 fetch·파싱 로직은 0줄 변경 확인.
- `v10.html`: 공훈전자사료관 오픈API 연동 탭 추가. 필드명 오류(`성명`→
  `NAME_KO`) 수정 → HTTP-only API와 HTTPS 배포 간 mixed content
  차단(구조적, 미해결) → 공식 문서상 `nameKo` 파라미터가 실제로는
  서버에서 무시됨을 실측 확인 → 전체 순회(약 382페이지) 방식 전환 →
  순회 중 서버 XML 자체의 명세 위반으로 파싱 재중단(139/382페이지
  지점)까지, 실패 원인이 바뀔 때마다 갱신 기록. **현재도 미해결.**

## V. 결론

세 트랙(본체/Provenance/시각화) 모두 같은 데이터를 다루지만 목적이
다르다 — 본체는 "사건을 어떻게 표현할까", Provenance는 "그 표현이
실제로 검증됐는가", 시각화는 "그걸 어떻게 보여줄까"에 답한다. 매
단계마다 "고쳤다고 생각한 문제가 재발하는" 패턴(오산학교 개교일,
CLM-023 재발, 공훈 API 시행착오)이 반복됐고, 이는 개별 실수가
아니라 **검증 없이 결정만 내리고 실제 파일에는 반영하지 않는 작업
방식 자체의 위험**으로 이 프로젝트 전체가 거듭 확인한 교훈이다. 이
교훈은 이 문서 자신에게도 예외가 아니다 — §III의 CLM-023·CLM-014
서술이 겪은 과잉확신과 재검토 과정 자체가 그 실례다.

(간결본)를 병합하기 전에 겹치는 사실관계를 대조.

- 두 문서가 공통으로 다루는 v1~v8 구간(8단계, 스키마 전환기/정합성 보강기/
  사실검증기 구분)은 서술 상세도만 다를 뿐 수치·순서 불일치 없음.
- 간결본이 요약하는 v9 계열 최종 수치(34 Core + 5 Hold + 16 Exclusion = 55,
  TTL 987 트리플)는 실제 산출물(`v9.5_claim_core.csv` 등)과 대조해 정확함.
- 간결본의 v10 서술("공훈전자사료관 연동 미해결")은 순수 추가분임.
> 결론: 병합 시 상세본의 v1~v8 서술을 그대로 두고, 
> 간결본의 개관을 맨 위에 얹은 뒤,
> v9~v10 상세 이력을 상세본과 같은 문체로 새로 이어 붙이면
> 정합성 문제 없이 하나의 문서로 합쳐진다고 판단. 
> 이렇게 최종본 완성함.
