# 온톨로지 프로젝트 전체 이력 (v1 → v10, 통합 최종본) [26.09.26 재확인]

## I. 개관

일제강점기 독립운동-근대학교 온톨로지는 두 데이터 트랙과 하나의 시각화
트랙으로 발전했다.

-   **본체 (v1~v8)**
    : Prof. 김현 & Prof. 김바로 style 계승.
    이항관계(v1) → 사건유형별 클래스(v2) → 단일 Event 스키마 정착(v3) →
    편찬 메타데이터·도메인 확장(v4\~v5) → 사실 검증(v6\~v7) → 불확실성
    자체의 모델링(`hasValidationStatus`, 신흥강습소 실체분리, v8).
-   **Provenance 트랙 (ver2\~ver5, v9.1\~v9.5)**
    : v8 인스턴스가 실제로 근거를 갖췄는지 재검증하기 위해 별도로 시작한 Claim 중심 병렬
    데이터셋. 49개 원본 항목 → 55개 Claim으로 분해
     → 34 Core + 5 Hold(TTL 반영, 987 트리플) + 16 Exclusion(CSV만 보관).
-   **시각화 (v6\~v10, dh-webpage 저장소)**
    : 본체·Provenance 트랙
    데이터를 브라우저에서 읽어 그리는 뷰어들. `v9_5re.html`에서 데이터는
    그대로 두고 의미론 재검토 표시축(`SEMANTIC_REVIEW`)만 추가했다.
    `v10.html`은 여기에 국가보훈부 공훈전자사료관 API 연동을 시도했으나
    **HTTP-only API·가용성 불안정·서버 XML 명세 위반 등으로 아직 실사용
    가능한 상태가 아니다**. [즉, 현재도 진행 중인 미해결 과제]

> 세 트랙은 김바로, 『제도-인사 온톨로지 설계』의 사건모델(`:Event` 단일 스키마)을 공통 뿌리로 삼는다. 
> 다만 Provenance 트랙은 그 모델이 표현하지 못하던 **관계 자체의 확실성**을 담기 위해 
> Claim/Evidence/Source를 분리한 별도 스키마로 갈라져 나온 것이며, 
> v8의 다음 버전이 아니라 병렬 재검증 트랙이다.

## II. 상세 이력 - 본체(v1\~v8)

### 1. 전체 개요 - 세 가지 접근(시기/방법/국면)

- **스키마 전환기 (v1~v3)**: 데이터를 어떤 구조로 담을지 결정. 이항관계
  → 사건유형별 클래스 → 원 논문의 단일 Event 스키마.
- **정합성·범위 확장기 (v4~v5)**: 편찬 정보(누가·언제) 정리, 중복·충돌
  개체 해소, 도메인을 "구한말 관공립학교"에서 "독립운동-근대학교
  네트워크"로 확장.
- **사실 검증·불확실성 모델링기 (v6~v8)**: 실제 역사적 사실을 재검색해
  확정하거나, 확정 못 하는 상태 자체를 구조화.

### 2. v1 --- 이항관계

- *솔직하게 밝힙니다.* 
- 60일 이내에 작업을 끝낼 수 있게끔 **클로드[무료 기본 버전:소넷5]와 챗지피티[무료 기본 버전:GPT-5.5 Instant~GPT-5.6 Luna]를 이용해 이항관계가 나오는 인물과 사건을 먼저 조사**했습니다.
  (실제 v9.5까지 작업은 60일 이내 끝냈고, 서류 작업으로 인해 총합 70일 정도 소요했습니다. )
- 나머지 작업 경우 논리 전개는 제가 했고, 시각화 등 부가적인 건 클로드와 챗지피티 활용했습니다.
 (특히 재검증 과정에서 csv와 보고서 수치 분석[=정합성 분석]은 클로드 이용했습니다.)

### 3. v1 → v2 --- 이항관계에서 사건유형별 클래스로

v1은 `["이승훈", "오산학교", "설립"]` 배열을 그대로 `forceLink`에 넣는
D3.js 그래프였다. v2에서 OWL/Turtle로 전환하며
`FoundingEvent`·`RoleEvent`·`AppointmentEvent`처럼 사건유형별 클래스를
만들었다.

### 4. v2 → v3 --- Event 모델을 기본 틀로 채택

v2에서 김바로 교수 박사논문을 적용할 수 있게끔 틀을 마련했다면,
v3에서는 논문의 Event 중심 설계를 기본 모델로 채택해 단일 `:Event` 클래스로 전체 통합.
47개체·627 트리플이며, Protégé 정상 파싱을 확인했다.
또한 `locatedIn`류 6개 관계는 Event로 바꾸지 않고 조직의 정적 상태로 남겼고,
자세한 사항은 v3.ttl 상단에 작성하였다.

### 5. v3 → v4 --- 편찬 메타데이터와 정합성 정리

`hasCompiler`/`hascompiledTime` 미기입 65건을 보강하고, 
`:백오인사건`의 Group/Event 이중 타입을 해소했으며, 
중복개체(`:이승훈설립오산학교_01`)를 제거했다.

### 6. v4 → v5 --- 편찬자 실체화, 도메인 확장

`hasCompiler` placeholder를 `:iteratorfor42`로 치환(68회)했다. 
다만 v5는 다음 문제를 방치(미해결)했다.

-   오산학교-대성학교 `succeedByPersonTo`가 근거(`hasBibo`) 없이
    서사만으로 단정돼 있었다.
-   안명근체포 Event가 `hasEventType :임명`으로 잘못 분류된 채 남아
    있었다. 당시 `:체포` Term 자체가 없었다.
-   역사적 사건 6개 전부가 `hasEestimation` 없이 "1월 1일" sentinel로 남아 있었다.

### 7. v5 → v6 --- 3회차 검토안 반영 (참고> ver.5부터 버전 안 늘리려고 5.1, 5.2 이런 시으로 작업.)

**필수 수정 4건**: 안명근체포 유형(`:체포`)·시간(1910-12-01) 정정,
오산-대성 승계관계 삭제, 오산학교 개교일 1907-12-24 확정
(다출처 일치 근거 존재. 단, 이 확신은 훗날 v9 ver2 검증 과정에서 재반박(논의)됨 --- §III 참조),
안명근체포→안악사건→백오인사건 2단계 확대구조 신설.

**추가 검증 날짜 5건**:
삼일운동(1919-03-01)·봉오동전투·청산리전투·조선물산장려회(1920-08-23)를
확정하고, 연도만 아는 설립 Event에는 일괄 추정 플래그를 부여했다. 
이 시점까지도 소속/참여 Event 12+9건은 언급 없이 공란이었다(v6 changelog에 미기재).
참고> 여기서의 changelog는 ttl 상단의 설명과 자체 검증 보고서를 의미한다.
     이런 작업이 모여 현재 이 문서[;온톨로지 프로젝트 전체 이력] 작성됨.

### 8. v6 → v7 --- 날짜 자동상속 금지 원칙의 최초 대규모 적용

신민회/임시정부 소속 12건에 Year 추정을 부여하고, 
3·1운동 참여 9건 중 6건을 확정하고 3건(정춘수·박희도·조만식)은 예외 처리했다.
설립과 공동설립을 구분하기 위해 `:공동설립` Term을 새로 도입했다.

이종일의 "경영"이 보성학교 전체가 아니라 
부속 인쇄소 보성사였음을 검증 코멘트로 처음 인지했으나(v7), 
트리플 자체는 아직 `:보성학교`로 남아 있어 "코멘트가 데이터를 정정하는" 결함이 존재했다.
(달리 말해, 인간의 직접 검증과 AI 검증 코멘트 간 불일치가 발생하여 이런 결함이 나온 것.)

### 9. v7 → v8 --- 불확실성 자체의 모델링

임시정부 소속 4건을 개별 재검증했다.

-   이승만: 1919-09-11 확정.
-   이동휘: 1919-09±2개월로 범위 조정.
-   이동녕·이시영: 간접인용 상태로 미재확인 표시. 
    필자가
    한국민족문화대백과사전 인용을 채택했으나 원문 URL을 직접 재확인하지 못했음을 명시했다.

이종일-보성사 구조를 분리하기 위해 `:보성사` Group을 신설해 v7의 결함을 해소했다. 
또한 `hasValidationStatus`를 신설해 김좌진-신민회를 "검증보류"로 격리했다. 
이는 원 논문에 없던 속성을 프로젝트에서 추가한 것이다. 
신흥강습소/신흥무관학교도 실체를 분리해 개칭 이벤트 존재 자체의 불확실성을 모델링했다.

**v8이 P1(다음 라운드 우선순위)로 명시적으로 이월한 항목**

1.  홍범도 전투참여의 Month 단위 날짜 보강.
2.  북로군정서 김좌진/서일 역할 비대칭(총재 vs 사령관) 반영.
3.  천도교 소속 3건(손병희·오세창·최린) 재검색.
4.  안명근-안악사건 "참여" 관계와 기존 체포/확대 이벤트 체인 간 의미 중복 정리.
    

안명근-안악사건 문제는 §III의 사후 발견에서 보듯 
v9.4까지 이어지며 형태를 바꿔 재등장한다. 
즉 v8에서 P1로 이월한 항목이 Provenance 트랙에서도 완전히 해소되지 않은 채 이어진 것.
(문제는, 필자 지식으로는 이런 문제에 대한 온톨로지 처리를 하기 힘들다는 점.
그래서 v8까지 본인 논리로 구현 확정하지 않은 것들은 이월했다.)

## III. Provenance 트랙 상세 (v8.1\~8.5, v9.1\~v9.5)

Provenance 트랙은 v8을 검증하는 별도 트랙이며, 
**v8의 다음 버전이 아니다.**

### 1. v8.1\~8.5 --- 방법론 설계

URL 팩트체크(ver2) → Claim/Evidence/Source 분리(ver3) → 김좌진
정정·Claim 분해(ver4) → 설계 승인 및 Rule G-01\~G-08 확정(ver5)의 순서로 진행했다.

ver2 단계에서 「이승훈」 항목 원문을 재검증해 보니 "11월 24일"로 되어 있었다. 
이에 따라 v6이 "복수 출처 일치"로 확정했던 
"12월 24일"의 근거 자체가 두 계열 출처를 짜깁기한 것이었음이 드러났다.
(참고> 이런 문제 때문에 그냥 최종 시각화에 본인이 참고한 출처 url을 그대로 명시한 것이다.)

### 2. v9 초안~완성본

49개 항목을 43개 행으로 매핑했으나, 오판 6개가 UNMAPPED로 남았다. 
원본과 대조해 누락 3건(신흥무관학교·대한독립군·양기탁)을 복원하고 
46개 매핑 항목을 확보했다. 
이후 다수 항목을 §4의 6개 표준 패턴에 따라 복수 Claim으로 분해했다
(예: 대성학교 1항목→CLM-002/011 2건,
오산학교 1항목→CLM-OSAN-01/02 2건). 최종적으로 커버리지를 확보한 55개
Claim을 완성했으며, 이 단계는 아직 신뢰도 필터링 전이었다.
> (참고> 이 내용 또한 인간 필자의 실수와 AI 검증 내용이 잘 드러난다.
>  인간은 AI보다 논리 전개에 더 뛰어날 수 있으나, 검증 과정에서는 AI가 더 빠르고 정확하다.)

### 3. v9.1

구조 검증 단계에서 CLM-023(SRC 오배정)과 CLM-010(비표준 precision)을
수정했다. TTL은 1155 트리플이었다.

### 4. v9.2

39개 포함(당시 "High-confidence"로 잘못 명명)과 16개 exclusion을 최초 분리했다. 
재검증 과정에서 CLM-006 컬럼 밀림, CLM-023 재발, CLM-010 재발,
안악사건(item 15) 완전 누락을 발견·수정했다. TTL은 928 트리플이었다.
(참고> 참고로 v8이 잘못되었다는 말이 아니다. v9에 검증이 더 강하게 들어가고, 
      온톨로지 구축에 대한 필자의 논리가 더 강하게 개입하게 되면서 문제가 발생한 것이다.)

### 5. v9.3

39개를 34 Core + 5 Hold로 재분류하고, 4단계 판정(유지/수정/보류/제외)을
확정했다. TTL은 969 트리플이었다.

### 6. v9.4

Claim 문장·URI·relation 의미 정합성 6건을 수정했다(CLM-014 subject 오류,
CLM-003 방향 불일치 등). `not_applicable` vocab를 새로 만들었다.(하지만 vocab 작업 번거로워서 곧 폐기함) 
TTL은 972 트리플이었다.

### 7. v9.5

`date_status`를 완전히 정합화해 빈 값 0건을 달성했다. 
1차 제안 규칙("date_value 없음→전부 not_applicable")이 자기모순임을 
재검토에서 발견해 폐기하고, 
"Claim의 시간적 의미"를 기준으로 규칙을 재수립했다
(not_applicable 9건/not_directly_verified 6건).

TTL은 **987 트리플**이며, Core 34 + Hold 5 + Exclusion 16 = 55다.

### 8. 사후(이후) 발견 --- 의미론 재검토와 과잉확신 정정

3자 비교분석에서 core+hold 39건 안에
`CLM-014`(`:안악사건 --related_to--> :105인사건`)가 존재함을 확인했다.
다만 `relation=related_to`는 인과관계·단순연관·사건 확대를 구분하지 않는 범용 값이므로, 
이 Claim만으로 "안악사건→105인사건"이 어떤 종류의 관계인지는 특정되지 않는다.

## IV. 시각화 트랙 상세 (v6\~v10, dh-webpage)

### 1. v6.html

TTL을 fetch로 읽어 GIS+관계망 2탭으로 렌더링했다. 
`ttl-parser.js`로 Event를 두 개의 간선(`hasPreObject→hasObject`,
`hasObject→hasPostObject`)으로 "접어" 표시했다.

### 2. v6_with_gonghun.html

관계망 탭에 v1 스타일 필터·검색 UI를 이식하고, 
공훈전자사료관 연동을 최초 시도했다. 
당시 필드명 버그로 0명 매칭이 발생했다. 
이 버그는 이후 `v8_with_gonghun.html`에도 그대로 이어졌다가 v10에서야 발견 & 수정.

### 3. v8_d3style.html / v8_with_gonghun.html

v1의 D3 코드 자산을 v8 데이터로 재현했다. 이 과정에서 버그 3건(숨은 탭
초기화, CSS grid 높이, `versions-data.js` 스키마 사고)을 발견·수정했다.

**\[해결\] v8 트리플 수 불일치(982 vs 985)**

`v8_with_gonghun.html`의 화면 표시 트리플 수(982개)가 `v8.ttl` 원문을
rdflib로 직접 파싱한 결과(985개)와 3건 차이 나던 문제를 조사했다.
`ttl-parser.js`와 `v8.ttl`을 Node.js로 나란히 실행해 재현을 시도한 결과,
현재 코드·데이터 조합에서는 985개로 rdflib과 type별 구성까지 완전히 일치했다.

-   Ontology 1
-   Class 5
-   ObjectProperty 15
-   DatatypeProperty 14
-   Term 18
-   Group 14
-   Person 31
-   Event 74

총합만 우연히 같은 것이 아니라 구성 요소 단위로 검증했다. 
따라서 현재 파서에는 트리플을 누락시키는 버그가 없다. 

(아마 982 경우 필자가 5 대신 2를 잘못 누른 듯하다.)
>참고> 앞서 언급한 1/5/15/14/18/14/31/74(합 172) = 개체(instance) 수 관련 추가 설명.
>예를 들어 Event 인스턴스 74개는 각각 hasObject, hasEventType, hasTimeValue, hasCompiler 등 평균 5~6개 트리플을 갖고 있으니, 
>172개 개체가 985개 트리플을 만들어내는 건 인스턴스당 평균 5.7개 트리플이라는 뜻이다.
>본 프로젝트의 스키마(속성이 각 Event/Group/Person에 여러 개씩 붙는 구조)를 감안하면 자연스러운 비율이라 생각한다.

또한 위의 검증 과정에서 인물 수 30(UI 배열 `ONTOLOGY_PERSONS`)과 
31(rdflib의 `rdf:type :Person` 카운트)의 차이도 해소됐다.
편찬자 메타 개체 `:iteratorfor42`가 `rdf:type :Person`으로 선언되어
rdflib 카운트에는 포함되지만, 역사적 인물만 보여주는 UI 배열에는 의도적으로 제외되어
있었다. 따라서 이는 버그가 아니다.

### 4. v9_5.html

Provenance 트랙의 최초 뷰어다.
`claimDecision`(core 실선/hold 점선)으로 신뢰도 구분을 표시했다.

### 5. v9_5re.html

데이터는 `v9_5.html`과 완전히 동일하다. 
`SEMANTIC_REVIEW` 참조표(CLM-024·CLM-027-04 2건)로 
"의미론 재검토 권고" 표시축만 추가했다.
diff 기준으로도 데이터 fetch·파싱 로직은 0줄 변경으로 확인됐다.

### 6. v10.html + gonghun_match.py

공훈전자사료관 오픈API 연동 탭을 추가했다. 
필드명 오류(`성명`→`NAME_KO`)를 수정했으나, 
HTTP-only API와 HTTPS 배포 간 mixed content 차단이라는 구조적 문제가 남았다. 
공식 문서상 `nameKo` 파라미터가 실제로는 서버에서 무시됨을 직접 확인했고, 
브라우저 호출을 포기하고 `gonghun_match.py`(로컬 실행 스크립트)로 
전체 순회(약 382페이지) 방식으로 전환했다. 
그러나 순회 중 서버 XML 자체의 명세 위반으로 139/382페이지 지점에서 파싱이 재중단됐다. 
실패 원인이 바뀔 때마다 갱신 기록을 남겼으며, api는 **현재도 미해결**이다.

## V. 결론

세 트랙(본체/Provenance/시각화)은 같은 프로젝트를 다루지만 목적이 다르다. 
본체는 "사건을 어떻게 표현할까", Provenance는 "그 표현이 실제로 검증됐는가", 
시각화는 "그걸 어떻게 보여줄까"와 관련 있다.

세 트랙 모두 성격은 좀 다르지만. 
매 단계마다 "고쳤다고 생각한 문제가 재발하는" 패턴(오산학교 개교일,
CLM-023 재발, 공훈 API 시행착오)이 반복됐다. 
이는 개별 실수뿐 아니라 **검증 없이 결정만 내리고 실제 파일에는 반영하지 않는 작업 방식의
위험**을 보여주며, 이런 위험을 체감했기에 더더욱 검증을 여러 차례 반복했다.

## VII. 정합성 분석 메모 --- 병합 및 교차검증 기록

기존 `verification_report_v1-v8.md`(상세본)와
`verification_report_v1-v10.md`(간결본)를 병합하기 전에 겹치는 사실관계를 대조했다.

-   두 문서가 공통으로 다루는 v1\~v8 구간(8단계, 스키마 전환기/정합성
    보강기/사실검증기 구분)은 서술 상세도만 다를 뿐 수치·순서 불일치가 없었다.
-   간결본이 요약하는 v9 계열 최종 수치(34 Core + 5 Hold + 16 Exclusion
    = 55, TTL 987 트리플)는 실제 산출물(`v9.5_claim_core.csv` 등)과
    대조해 정확함을 확인했다.
-   간결본의 v10 서술("공훈전자사료관 연동 미해결")은 순수 추가분이었다.
-   병합 과정에서 §IV에 `v6_with_gonghun.html`이 누락됐던 것을 발견해 추가했다.    
-   이후 교차검증에서 §III의 CLM-023 재발 횟수 서술과 사후 발견 문단의
    과잉확신 두 곳을 추가로 정정했다.
-   §IV의 v8 트리플 수 불일치(982 vs 985)는 실제
    `ttl-parser.js`·`v8.ttl`을 Node.js로 재실행해 해결했다. 
    인간의 타이핑 오류로 985 대신 982를 쓴 것으로 결론내렸다.

이 정합성 메모는 문서 간 대조와 명시된 재현 검증을 기록한 것이며,
